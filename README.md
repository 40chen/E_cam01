# ESP32S3 Ecam

立创·实战派 ESP32-S3 开发板（LCKFB-SZPI-ESP32-S3-VA）的 ESP-IDF 固件。取 GC0308 画面、320x240 实时预览（带黑白 / 负片滤镜）、照片以 JPEG 存 FAT32 TF 卡，播放 TF 卡里的 MP3（旋转黑胶大图模式），WiFi 与邮箱配置存在 NVS 里。另有两处"整机形态"开关：把 TF 卡交给电脑的 U 盘模式，以及收上位机状态的副屏显示。

界面文案一律是英文（LVGL 内置字体不含汉字，中文只出现在文件名上，那条路用了一个专门的 GB2312 子集字库，见 `ui_theme.h` 的 `UI_FONT_CJK`），所以下文提到屏幕上那几栏时保留英文原文。

## 构建与烧录

### 开机反复重启、崩在 `esp_psram_init`（2026-09-25 记）

现象：串口里每次启动都停在

```
I (720) MSPI Timing: PSRAM timing tuning index: 5
Guru Meditation Error: Core 0 panic'ed (LoadProhibited)
PC: esp_psram_init at components/esp_psram/esp_psram.c:136
```

而且复位原因全是 `rst:0xc (RTC_SW_CPU_RST)`（软件复位）。

**先看一件事就能判断是不是固件的问题**：日志里有没有 `app: app_main entered`
（`app_main()` 的第一行）。**这行没出现 = app 代码一行都没跑**，那崩的就只能是
芯片自己的初始化，和业务代码无关——别再去二分自己的代码了。

**根因是"热复位不给 PSRAM 断电"**：PSRAM 芯片（尤其是八线 octal 那种）被上一次
运行配置过之后会留着状态，热复位时重新初始化就可能失败。而

- 按板子上的 RST / EN 键 → 热复位
- `idf.py flash` 之后 esptool 拉的 RTS → **也是热复位**（只拉复位脚，不断电）
- monitor 里的重启 → 热复位

**只有把 USB 线拔掉（真的断电）才能清干净。** 拔掉等一分钟再插。

如果时好时坏（`PSRAM timing tuning index: N` 是每次上电现算的校准值，器件临界时
可能选到坏点），把 PSRAM 降速当缓解：

```
sdkconfig.defaults:  CONFIG_SPIRAM_SPEED_40M=y   （替掉原来的 _80M）
然后删掉 sdkconfig 重新构建
```

**这一节的教训（比结论更重要）**：当时"加了一段代码就崩、注释掉就好"看起来像
铁证，但其实**每次对照只有一次试验**，而故障本身就是间歇性的——这种"1 位差异
+ n=1"的对照不构成证据。真正定案的是那份"第一次启动日志里没有 `app_main
entered`"：**先确认代码有没有跑，再去查代码。**

**2026-09-25 的处理和解法**：崩的 PC 在 **IROM**（代码在 flash 里执行）、
`EXCVADDR = 0`（NULL 解引用）——flash 读取出错会返回一串 0，解引用就是 NULL，
而 PSRAM 那时还没映射上。判断是 flash/PSRAM 时序临界，**两处都降到 40MHz 之后
就正常了**：

```
CONFIG_SPIRAM_SPEED_40M=y
CONFIG_ESPTOOLPY_FLASHFREQ_40M=y
```

两处是一起改的，所以**暂时分不清是哪一侧临界**。稳定之后想分清，一次改回一个
（先试把 flash 改回 80M）就能判定——但既然降频之后没问题，没必要为了归因去
复现一个会崩的状态。**代价是 flash 40MHz 会略微拖慢启动和 SPI 读取。**

⚠️ **改 `sdkconfig.defaults` 时注释一律写英文**：kconfgen 用平台默认编码
（中文 Windows 上是 GBK）读这个文件，一个中文注释就会让整个构建失败——
报错是 `UnicodeDecodeError ... gbk codec ...` 加一句 `Failed to run kconfgen`，
看起来像构建系统坏了，其实只是一个注释。


1. 装 ESP-IDF 5.1 或更新版本，并 export 环境。
2. 设置目标：`idf.py set-target esp32s3`。
3. 构建：`idf.py build`。
4. 烧录并看串口：`idf.py -p COMx flash monitor`。

所有配置都在触摸屏上填、存 NVS，没有任何编译期配置。

## 主菜单

3x2 六张卡：

```
Camera  |  Music   | Work Mode
Photos  | Settings | Modules
```

左边两列是"看和听"，右边一列是"改设备形态和状态"。**加功能时不要挪左边那四个格子**，它们已经有肌肉记忆了；新卡一律往右列加。

格子尺寸是**算出来的不是试出来的**：根对象 pad 10 → 内容宽 300，两处列间距各 8 → `(300-16)/3 = 94`；高 240 减上下 pad 20、状态条 22、状态条下的 pad_row 6 得 192，再减一处行间距 8 → 92。改 pad 或间距要跟着重算，否则 flex 会折成 2+4 而不是 3+3。

格子从 2x2 时的 146 宽掉到 94 之后，**按钮主题自带的 `pad_hor`（16）会把标签挤到只剩 62px**，所以 `page_home.c` 里把格子的 padding 清零了；标签限宽 100% + 居中，放不下自然折成两行（图标只占顶上约 42px，下面够两行）。不要用 `LV_LABEL_LONG_DOT`，那个会显示成 "Work Mo…"。

**`Work Mode` 当前是折成两行的**：拿 `tools/measure_font.py` 量出来是 95.1px，格子只有 94px。其余五个标签最长的是 `Modules` 69.4px，都宽宽松松。折行的样子（`Work` / `Mode` 居中两行）看着不坏，所以先留着；**真要收成一行有两条路**：把 `GRID_GAP` 从 8 收到 6、格子变 96（余量只剩 0.9px，太紧），或者这个标签单独降到 14 号（83px，余量充足）。

## 工作模式（Work Mode）

主菜单 → **Work Mode**。放的是**会改变整机形态**的开关，而不是设置项——设置页管凭据和参数（填一次就不动），这里的每一项都会让设备换一种工作方式，用户找它们时想的是"切个模式"。

| 那一行 | 作用 |
| --- | --- |
| `USB Drive` | 把 TF 卡作为 U 盘交给电脑（原来挂在设置页 STORAGE 分组下） |
| `Status Display` | 开关：开始从串口收上位机推过来的状态 |
| `PC Status` | 进副屏页看那些数据；开关没开时点它会提示先去开开关 |

**Status Display 开关的状态只存在内存里，掉电回到关**：它要上位机那头一直在跑才有意义，开机自动把串口收起来、而对面根本没在发，只会让人以为功能坏了。`Status Display` 的开关是按 `app_pcmon_is_running()` 摆的，不是某个页面变量——离开这一页再回来，它得跟正在跑的东西一致。**接收任务也不随页面销毁而停**：它跟的是"模式"不是"页面"。

`USB Drive` 做成**可点的行**而不是开关：它点进去就换个形态，不是拨一个持续的状态。

> 这一页曾经还有一项 **`USB Display`**（把整机变成电脑的一块显示器，走原生 USB 口推 JPEG 画面），2026-09-26 移除。它要装一个 Windows IDD 驱动才能用，而那个驱动在目标机器上起不来（设备管理器报代码 10），**决定不适合产品定位**。代码和结论存档在 `_removed/README.md`。

## 副屏显示（PC Status）

上位机推、板子收、屏幕显示。数据是上位机**每秒往串口写一行 JSON**：

```json
{"type":"status","host":"DESKTOP-X","cpu":12.3,"ram":45.6,"gpu":-1,
 "net_up":1.2,"net_down":3.4,"battery":-1,
 "api":{"base_url":"...","key_set":true,"tokens":123,"cost":1.23,
        "balance":45.67},"ts":12345}
```

**左右分栏 + 底行对称**：

```
DESKTOP-X  live
SYSTEM                  API (CNY)
CPU            12.3%    Tokens        1.23M
RAM            45.6%    Cost           12.34
GPU               1%    Balance        45.67

[N] 12.3 KB/s              [M] 4.5 KB/s
```

（`[N]` / `[M]` 是 FontAwesome 的上下箭头字形，见下面"界面字体能显示什么"。）

- **为什么分栏**：CPU/内存 和 API 用量这两组数据没有关系，上下排会让人顺着往下读、以为是一组。
- **为什么网速单独提单行**：它带单位、字符串最长，夹在栏里会把栏宽撑到别处放不下。提到整幅宽的底行之后，一个贴左一个贴右，两栏也都松快了。
- **电池那行删掉了**（台式机上它一直是 N/A，白占一行）。上位机还在发这个字段，固件**刻意不解析**，见 `app_pcmon.h`。
- **字号：标签 16 号、值 20 号**。屏幕只有 320x240、内容区 304x190，所以这一页**不用 `ui_list_row_create`**（那个行高 30 多），自己排一组 30px 的紧凑行。**下面每个数都是拿 `tools/measure_font.py` 量出来的**：

      竖：状态行 20 + 小节标题 22 + 3 行 × 30 + 网速行 30 = 162 ≤ 190
      横：左栏 130 + 间距 8 + 右栏 166 = 304
            左栏要塞 "RAM"(16) + "45.6%"(20) = 97.2
            右栏要塞 "Tokens"(16) + "99999999"(20) = 157.4  ← 全场最长的一行
            底行一侧要塞 "12345.6 KB/s"(20) + 箭头 ≈ 144 ≤ 152（半幅）

  右栏比左栏宽是有意的：API 那三个标签（尤其 `Balance`）比 `CPU`/`RAM` 长得多。**改字号或改文案之前先量一遍**——这块屏上"差 1.5px 就挤到标签上"是常态。

  **24 号做过一版，用户反馈"大了些"**，所以降回这一档；降完之后右栏多出 30px 余量，Tokens 的阈值跟着放宽（见下）。
- **Tokens 那一行只有 8 个字符位**，超了才压成 **3 位有效数字 + 10 的次方**（`%.2e`）。

  | 值 | 显示 | 字符数 |
  | --- | --- | --- |
  | `99999999` | `99999999` | 8 ← 上限 |
  | `100000000` | `1.00e+08` | 8 |
  | `999999999` | `1.00e+09` | 8 |
  | `12345678901` | `1.23e+10` | 8 |

  - 8 是量出来的：八位（`"99999999"` = 98.5px）加标签 `Tokens`（58.1px）是 156.6px，塞得进 166px；九位就顶到标签上了。**能显示全就显示全**——8 位以内一律照原样打整数，用户要的是看见用量；只在真放不下时才换记法。**余额和已消费从来不压缩**，那两个是要精确看的。
  - ⚠️ **用 C 库的 `%.2e`，不要自己算位数。** 自己归一化最容易在"尾数进位"上翻车：`999999999` 先按 9 位数取指数 8，尾数 `9.99999999` 用 `%.2f` 一舍入就成了 `10.00`，拼出来 `10.00e+08`——既不是规范写法（尾数该在 [1,10)），又**正好 9 个字符、把 8 个字符位的上限撑破**。根因是"先定指数、再舍入尾数"，而舍入结果可能又跨一个数量级。C 库的 `%.2e` 是先规范化、再舍入、发现进位就重新规范化，直接给 `1.00e+09`，并且稳定 8 个字符。**这一类"边界上进位"的活交给库做，别手写。**
  - **不要换成 `lv_label_set_text_fmt()`**：那个走 LVGL 自己的 printf，不支持浮点，`%.2e` 会打出字面的字符（见下面"LVGL 的 printf 不支持浮点"一节）。这里用的是 `row_set()`，走 C 库 `vsnprintf`，没问题。
  - （中间试过一版"去掉 `+` 和前导零"的简写 `1.23e8`，长度更短但读起来不如标准写法，已改回 `%.2e`。）
- **网速 1000 KB/s 以上换算成 MB/s**：一是好读，二是 `"12345.6 KB/s"` 这种四位数加小数点会把底行两侧顶到一起（两侧合起来只有 304px，各占一半）。

### 上位机

`host control/Ecam_display/Ecam_Status_Display.py`（`build.bat` 打包成同目录的 exe）。系统状态那部分独立于串口一直在刷；点 **开始传递数据** 才建发送线程。

**2026-09-23 起上位机不在这个仓库里了**：`E_cam/` 下分成了 `ESP32S3_Ecam/`（本仓库）、`ESP32C2_tank/`、`host control/` 和 `for_example/` 四个平行目录，上位机在 `host control/Ecam_display/`。所以 `tools/check_pcmon_payload.py` 是按 `../host control/Ecam_display` 这个相对路径找它的，找不到就用环境变量 `ECAM_DISPLAY_DIR` 指过去——它和固件不是一个仓库，路径还会动。

**2026-09-22 修掉的三个 bug，都是同一类：状态变量没人赋值。**

1. **一行 JSON 都没发出去。** `_start_monitor()` 只改了按钮文案、**从没建过 `_monitor_loop` 那个线程**（`self.monitor_thread` 在 `__init__` 里设成 `None` 就再没被赋过值）。界面写着"已连接，开始推送数据"，实际什么都没写——板子那边永远等不到数据。
2. **"停止传递数据"按钮失效。** `self.monitoring` 只在 `__init__` 里被设成 `False`、**再没被赋过值**，于是 `_toggle_monitor()` 永远走 `_start_monitor()`：点"停止"其实是**再去开一次同一个串口**，系统回一个"端口被占用"，弹出来的是「连接失败 / 无法打开串口 COM16」。看着像串口坏了或者被别的程序占了，其实按钮根本没接上。（修法是 `_start_monitor` 里置 `True`、`_stop_monitor` 里**先**置 `False` 再关串口。）
3. **网速算出来大得离谱。** `_monitor_loop` 原来和 `_system_monitor_loop` **共用** `self._last_net` / `self._last_time`。两条循环都是一秒一拍，对方刚更新过这边，`dt` 就接近 0。现在发送循环自己记一份基线。

**这三个都是"界面看着正常、数据是错的/没有"这一类**，靠看界面发现不了。所以 `tools/check_pcmon_payload.py` 现在不只查字段名，还会**真跑一遍开始 → 停止 → 再开始**，并且假串口**刻意模仿"端口被占用就抛异常"**——不模拟这一点的话，第 2 个 bug 在测试台上是看不见的（实测：把 bug 放回去，脚本会报出和你看到的一模一样的"无法打开串口…端口已被占用"）。

### 为什么用 UART0，以及它和控制台的关系

板子上那颗 **CH334F HUB** 把 Type-C 分给 CH340K，CH340K 接的正是 **UART0（TX/RX = GPIO43/44）**，电脑上看到的那个 COM 口就是它。所以副屏收的就是控制台那条线的 RX 方向。

**收 RX 不影响日志**，`components/vfs/vfs_uart.c` 里看得很清楚：日志走的是那个 VFS 的 `tx_func`，开机时指向 ROM 直写，**只有显式调用 `esp_vfs_dev_uart_use_driver()` 才会改成走驱动**。`app_pcmon.c` 装了 UART 驱动但不去调它，控制台的写法就一个字节都不动。反过来说，**别在那儿调 `esp_vfs_dev_uart_use_driver(UART_NUM_0)`**——那会把控制台的读写都接到这个驱动上，而我们从没打算给它当控制台用。

（`uart_driver_install` 在 IDF 5.1 里对应的卸载函数叫 **`uart_driver_delete`**，不是 `uart_driver_uninstall`——后者在 5.1 的头文件里根本不存在。写错的话是链接期的 `undefined reference`。）

### 几个实现上的取舍

- **整帧重建，缺的项回默认值，不沿用上一帧**。沿用的话，上位机哪天少发一个字段，屏幕上会继续显示旧数字，看着像实时值——那比显示 `--` 危险得多。
- **断线（3 秒没新帧）时保留最后一帧的数值**，只把状态行变橙。最后一帧常常正是用户想看的（上位机关机前那一刻的用量），清成 `--` 等于把唯一有用的数据扔了。
- **一行超长就整行丢掉**（768 字节上限），不拼接。宁可丢一帧也不要拼半行，半行解析出来的东西没法信。
- **非 JSON 的行静默丢弃**（DEBUG 级日志）。线太长、接触不良、上位机正在重启都会吐出半行，**解析失败是常态不是故障**，为它报错刷屏只会淹没真正的问题。
- 值右对齐成一行，眼睛顺着右边那列往下扫就看完了。箭头用 `LV_SYMBOL_DOWN` / `LV_SYMBOL_UP`——LVGL 内置的 montserrat **只覆盖 ASCII 加 FontAwesome 那一段**，直接写 `↓↑`（U+2193/U+2191）会是两个方框；同理 `¥`（U+00A5）也不在里面，所以货币单位写在 `API (CNY)` 这个标题上。
- `app_pcmon_stop()` **等不到接收任务退出就不卸驱动**：`uart_driver_delete` 会把驱动内部的缓冲和信号量都释放掉，而任务可能正卡在 `uart_read_bytes` 里，那是在释放中的对象上操作。留着一个没人读的驱动，远好过踩已经释放的内存。
- 顺手留了个 `tools/check_pcmon_payload.py`：**拦住上位机的串口、真跑一遍它的发送循环**，再把固件读的字段名从 `app_pcmon.c` 里抠出来比对。这两边是靠字段名耦合的，而且耦合失败时两边都不报错——上位机照常写、板子照常收，只是屏幕上一片 `--`，看起来像没插好线。

## WiFi 配置

设置页 → **Network** 会列出附近的 AP，按信号强弱排序，同一个 SSID 只占一行。选中一个：加密的会弹软键盘输密码，开放的直接连。

**没有手打 SSID 的入口，所以隐藏网络连不上** —— 驱动只能给它一个空 SSID，够不上建立连接所需的信息。

**Password** 是给当前选中的网络重输密码用的，不必重新扫描。**Status** 显示实时状态（`Connected 192.168.1.23` / `Connecting...` / `Auth failed` 等），失败后点它即重连。

连上之后 SNTP 对时（开机时已把时区设成 CST-8），照片名变成 `IMG_YYYYMMDD_HHMMSS.jpg`；首次对时之前退化成 `IMG_00001.jpg`。

## 邮箱配置

Mail 分组从上往下填，第一栏决定后面几栏。

| 那一栏 | 填什么 |
| --- | --- |
| `From` | 发件邮箱，例如 `zhangsan@qq.com` |
| `SMTP Server` | 按 `From` 的域名自动填；自建或企业邮箱才需要自己改 |
| `Port` | `465`。只实现了 465 隐式 TLS，587 的 STARTTLS 不支持 |
| `App Password` | **授权码 / 应用专用密码**，不是账号登录密码 |
| `To` | 收件人，任意邮箱，跟上面的 SMTP 服务器无关 |
| `Send Test Email` | 发一封纯文本测试信，用来端到端验证这套配置 |

SMTP 服务器是按 `From` 的域名推出来的（域名表在 `main/app/app_mail.c` 的 `s_smtp_hints`）。它只覆盖空值或它自己填过的值，手填的服务器永远不会被冲掉；端口空着时会补成 `465`。

两个前置条件，不满足时给的是明确文案而不是一个没头没尾的失败：

- 必须已连上 WiFi → `Connect Wi-Fi first`。
- 必须已由 SNTP 对时 → `Waiting for clock sync`。TLS 要用系统时间校验证书有效期，而 SNTP 只在第一次拿到 `IP_EVENT_STA_GOT_IP` 之后才跑，所以刚连上那几秒内发信会撞到这条。

已知限制：

- **Gmail、iCloud、Yahoo 必须用应用专用邮箱授权码（非邮箱登录密码）**，用登录密码会收到 `535`，界面显示 `Login refused`。
- **Outlook / Hotmail / Live 不支持**。微软只提供 587 + STARTTLS（未实现），且早已禁用密码认证、强制 OAuth2。域名仍然会被识别出来，这样界面能直接说明原因，而不是填一个连不上的服务器地址。

## 启动页图片

启动页显示的图来自 `assets/logo2.jpg`，由 `tools/gen_splash_logo.py` 转成
`main/ui/splash_logo.c`（320x240 的裸像素数组，直接编进固件）。

**换 logo 之后要重新跑一次脚本**：

```
python tools/gen_splash_logo.py
```

需要 ImageMagick（`magick` 命令）和 Python 3，不需要 Pillow。

几个设计取舍：

- **不在固件里解码**。启动页的意义就是盖住启动那段时间，显示前先解一次 JPEG
  （几百毫秒）等于把这段空白又还回去了。预转成裸像素是拿 flash 换启动速度，
  代价约 150KB。
- **四周留 8px 空白，图片不贴边**。改 `tools/gen_splash_logo.py` 里的 `MARGIN`
  即可。logo 是正方形，按留白后的高度缩放（当前 224x224），水平居中。
- **留白不是填固定色，是把坐标夹回图片范围取最近的边缘像素**（即向四周外扩边缘），
  让图片边缘与留白自然衔接。
- **字节序**：`CONFIG_LV_COLOR_16_SWAP=y` 时 `lv_color16_t` 的位域是
  `green_h:3, red:5, blue:5, green_l:3`，展开后两字节与标准 RGB565 相反，
  所以脚本存的是大端（高字节在前），跟相机预览那条路一致。

## 界面字体能显示什么

界面文案一律英文，不只是"习惯"问题：**LVGL 内置的 montserrat 只覆盖 ASCII（0x20~0x7E）
加 FontAwesome 那几个符号**（`lv_font_montserrat_16.c` 里那条 `unicode_list` 只有 62 项，
全是 0xF0xx~0xF2xx）。所以：

- `↓ ↑`（U+2193 / U+2191）**不在里面**，写出来是两个方框——要用 `LV_SYMBOL_DOWN` /
  `LV_SYMBOL_UP`（FontAwesome 那一段）。副屏页的网速行就是这么写的。
- `¥`（U+00A5）也不在里面（覆盖从 0xB0 才开始），所以货币单位写在标签上
  （`API (CNY)`）而不是值里。
- 要显示中文只有一条路：`UI_FONT_CJK`（见下面的"音乐"一节）。

每个内置字体的行高也要记着：`montserrat_14` 是 16、`16` 是 18、`20` 是 22、`24` 是 26。
排固定高度的行时用得上（副屏页那些 30px 的行就是照这个定的）。

## LVGL 的 printf 不支持浮点

**`lv_label_set_text_fmt()` 里写 `%f` / `%.1f` 不会打出数字，只会打出一个字面的 `f`。**

原因：LVGL 自带 `lv_snprintf`（`lv_printf.c`），**默认不支持浮点**——
`CONFIG_LV_SPRINTF_USE_FLOAT` 没开，那个 `case 'f'` 整段被 `#if` 包着。
格式转换符认不出来时会原样输出那个字符，于是

```c
lv_label_set_text_fmt(lbl, "%s %.1f KB/s", sym, kbps);   /* 屏幕上：  ↓ f KB/s */
```

**2026-09-22 副屏的网速那行就是这么废掉的**：数值全在（上位机在发、解析也对），
只是格式化那一步被吃掉了，屏幕上只剩一个 `f KB/s`，看着特别像"数据没收到"。
同一个函数里其他行是好的，因为那些走的是 `row_set()` 里的 **C 库 `vsnprintf`**。

支持的是：`%d %i %u %x %X %o %b %c %s %p %%`（长度修饰 `l/h/t/j/z` 也有）。
**要打浮点就自己 `snprintf` 到缓冲再 `lv_label_set_text()`**，或者把数改成整数
（比如网速存 KB/s 整数、用 `%d`），不要去开那个 config——为了一行字多链一套
浮点 printf 不划算。

**字宽不要估，量。** 这块屏只有 320px 宽，界面里好几处是按算出来的固定尺寸排的
（主菜单 94px 的格子、副屏页 130/166 的栏宽），估宽了标签顶到边或者折行、估窄了
白留一堆空隙，而且改一个字就得重新猜一遍。LVGL 的字体文件里每个字形都带着
`adv_w`，直接读出来就是准确值：

```
python tools/measure_font.py 20 "Balance" "45.67"
```

只依赖标准库，只支持 ASCII（内置 montserrat 的那段 cmap 是 format0_tiny，算得出来；
FontAwesome 那些符号在稀疏表里，要用得先把 `unicode_list` 也解出来）。

## 拍照

取景页铺满实时 QVGA 预览。拍照用屏幕上的圆形快门，或者板上的 **Boot 键**（GPIO0）。

**拍出来的照片是 640x480（VGA），不是预览的 320x240。** GC0308 是 30 万像素的传感器，640x480 才是它的原生分辨率，QVGA 只是它 4:1 抽样出来的。照片不该跟着屏幕分辨率走。

做法是**传感器全程跑 VGA，预览那一路在软件里缩一半**（`downscale_half()`，2x2 取左上角那点）。相机页收到的仍然是 320x240，不用改。

**为什么不能让传感器平时输出 QVGA、拍照时才切上去**：`cam_hal` 在 ISR 里会校验收到帧的长度和配置的 `fb_size` 是否相等（`driver/cam_hal.c`）：

```c
if (frame_buffer_event->len != cam_obj->fb_size) {
    cam_obj->frames[frame_pos].en = 1;   /* 不入队，且缓冲被永久标记占用 */
    ESP_CAMERA_ETS_PRINTF("cam_hal: FB-SIZE: %u != %u\r\n", ...);
}
```

对不上就不出帧，而且那块缓冲再也不会被释放——几帧之后所有缓冲全卡死，取帧一直 `timeout`，最后中断看门狗复位。**传感器只能全程一种尺寸。**

预览用双缓冲交替：`lv_img_set_src()` 只是换指针，真正的绘制在 LVGL 任务里，用一块的话下一帧会把正在画的那份覆掉，画面就是撕裂。

代价：帧缓冲从 2 x 153KB 变成 2 x 614KB，另加两块 153KB 的预览缓冲（都在 PSRAM，进出取景页时分配/释放）。PSRAM 带宽压力也上去了（VGA 20fps 光 DVP 写入就是 12MB/s，加上缩放读写约 28MB/s），预览帧率可能会掉。

Boot 键只在取景页打开时轮询 —— 它不是全局快门 —— 而且**按住不放只拍一张**：处理逻辑只有在检测到松开之后才会重新武装。

按下之后**画面定格 1 秒**。

定格冻结的是预览的最后一帧，而不是去读刚存下来的那个 JPEG 文件。预览本来就是同一颗摄像头、同一分辨率，肉眼分不出区别，却省掉了读卡 + JPEG 解码 + 153KB PSRAM。

### 滤镜

快门左右各一个药丸按钮：左边 **`B&W`**（黑白），右边 **`Neg`**（负片）。两个是一组单选，**再点一次当前那个 = 关掉**（回到无滤镜）——多一个"都不选"的出口，比在 56px 高的控制条里再塞一个 None 按钮省地方。

**走传感器寄存器，不是改预览的那些像素**。GC0308 支持特殊效果（`gc0308.c` 的 `set_special_effect`，写 0x23 寄存器低两位），所以**预览和存下来的照片一起变**，不用在 `downscale_half()` 和拍照两条路上各写一份像素变换。按钮那两个值直接就是 esp32-camera 的 effect 编号（`NEGATIVE=1` / `GRAYSCALE=2`），`app_camera.h` 里刻意不再加一层映射表——多一层映射就多一处会写错。

**滤镜每次进取景页都会重设一遍**：`bsp_camera_init()` 每次都会把传感器整套寄存器重写一遍，0x23 跟着回到 Normal，所以 `app_camera_start()` 里要把用户选的那一档补回去（只在非 Normal 时才写，Normal 是上电默认值）。选择存在 `app_camera` 里，跨页面活着，但**掉电不保留**。

**驱动里那个 `set_special_effect` 是靠源码读出来的，没在真机上验证过**（同一个文件里 3~6 号"色调"效果作者自己都注着 undocumented）。上板如果发现按了没变化，退路是在 `page_camera.c` 的 `on_frame()` 里做软件变换（灰度 = 取 RGB565 高字节加权，负片 = `0xFFFF - px`），代价是每帧 76800 像素的 CPU、帧率会掉几个 fps。**先看串口有没有 `set effect N failed`**：有就是传感器不认，没有就是写进去了但没生效。

### 快门声（2026-09-22 定稿：素材）

拍照时播一声"咔"。这个功能来回折腾了三轮，结论和过程都值得留着：

| 时间 | 状态 | 当时的原因 |
| --- | --- | --- |
| 2026-09-19 | 做完又移除 | 素材能量九成在 2~8kHz，而**原装小喇叭** 3~5kHz 以上就滚降 |
| 2026-09-22 | 换喇叭后恢复 | 编三个候选（`Raw`/`Loud`/`Body`）在板子上点着听，仍然不行 |
| 2026-09-22 | 换素材后定稿 | 换成 `clear-camera-shutter-sound.mp3`，**三个候选都有声音了**，选 `Raw` |

**一个诚实的保留**：两轮之间同时换过**喇叭**（2828 4Ω 3W）和**素材**，所以"到底是哪一个修好的"没有做隔离实验。用户的判断是素材问题，本工程按这个结论走；`Speaker Bands` 那 100 行扫频代码留在 git 历史里，哪天又要查可以从那儿捡回来。

**现在只有一个音色**（`Raw`：原素材只做峰值归一化）。当初为了"听着挑"写的三个候选和那张 `shutter_sound_variants[]` 表结构留着——以后要加音色，`tools/gen_shutter_sound.py` 里加一行、固件不用改。

**设置页 → SOUND** 只有两行：

- **`Shutter Sound`** 开关，控制拍照时出不出声；
- **`Volume`** 滑条，拖完松手会放一声快门声试听。

原来那三行测试工具（`Test Speaker` 放 440Hz 长音、`Shutter Sound` 换音色、`Speaker Bands` 扫六个频点）是排查期间的临时产物，定稿后收掉了。**诊断能力没丢**：拖一下音量滑条松手就出声，既听清了当前音量，也顺带验了"I2S → ES8311 → 功放"这条通路还通不通（原来那是 Test Speaker 的活）。

两个开关都**只存在内存里，掉电回到默认（开 / 50）**，跟音乐页那个音量一样。要落盘得给 `app_settings` 加键，还没做。

**实现上的讲究：**

- **声音放自己的任务里**（优先级 5，比 LVGL 的 4 高一点是为了让"咔"紧跟快门）。`app_sound_play_pcm()` 会阻塞在 I2S 写入上，写完还要等 DMA 排空，占着 LVGL 任务的话这段时间触摸采样整段丢失。
- **4KB 一块分块喂，不整段拷**。I2S 的 DMA 读不了 flash，必须先进可 DMA 的内存；整段拷（26544 字节）看着也行，但实测相机 + WiFi + LVGL 全跑着时一次性要 96KB 的 DMA 内存会直接失败。4KB 是稳拿的量。
- 写完要等 `SOUND_DRAIN_MS`(120ms) 再关功放，否则尾巴被切掉（最后那点余音"嘎"一声没了）。这个常数是按 I2S 的 6×240 帧 DMA、16kHz 下 90ms 定的，**换更低采样率的素材要跟着调**。
- 设置页那个音量滑条**必须先 `bsp_audio_init()` 再设音量**：`bsp_audio_volume_set()` 在没初始化时直接返回 `ESP_ERR_INVALID_STATE`，值既到不了 ES8311、也不会被 BSP 记下来——那样滑条拖了没反应，看着像滑条坏了。

**素材与生成脚本：** 源是 `assets/clear-camera-shutter-sound.mp3`（48kHz 立体声，415ms），脚本用 **ffmpeg** 解成 16000Hz / 16bit / 单声道再处理。换素材之后要重新跑一次：

```
python tools/gen_shutter_sound.py
```

依赖 ffmpeg 和 Python 3，不需要 numpy。**脚本会把素材的分频段能量占比打出来，别跳过那段**——这个功能栽过的两次都是"素材的能量落在喇叭放不出来的频段"，而**光用耳朵在电脑上是听不出来的**（电脑音箱能放的频段比这颗喇叭宽得多）。

那次排查留下三条结论，**现在依然成立**（原来记在已清空的 `_removed/README.md` 里，挪到这儿）：

1. **I2S 通道必须在 `bsp_audio_init()` 里 `i2s_channel_enable()`**。这句已经修好并留在
   [lckfb_bsp.c](ESP32S3_Ecam/components/lckfb_bsp/lckfb_bsp.c) 里，**不要删**——MP3 也要靠它。
   当初移植时把它删了（注释里还写着理由，而理由是错的），结果是 I2S 主时钟起不来、
   `i2s_channel_write()` 一个字节都排不进 DMA，症状极像硬件故障：ES8311 寄存器全对、
   功放也开着，就是没声音。
2. **内部 DMA RAM 很紧张。** 实测相机 + WiFi + LVGL 都跑起来之后，
   `heap_caps_malloc(96000, MALLOC_CAP_DMA)` 直接失败，16384 字节能拿到。
   **音频缓冲必须分块，一块一两万字节**，不能一次分配整段。
3. **别指望用软件"修"喇叭的频响。** 提高音量、加大数字增益、换采样率都试过，对"放不出来
   的频段"无效——那是物理限制。要重做就得换一个**低中频成分更足**的素材，或者换喇叭。

## 音量

两条滑条（音乐页大图模式的竖条、设置页 SOUND 组的 `Volume`）**写的是同一个值**，
所以调哪边都一样——**包括取景页按快门时那一声**。

- **值存在 `app_audio` 里**（`s_volume`，0~100，开机默认 50），最终落到 ES8311 的
  DAC 音量寄存器。0dBFS 在 93，所以 `apply_volume()` 把界面上的 0~100 线性映射到
  0~93 再写下去——**滑条每一格都有效**，不会出现"拖到最后几格没反应"。
- **切采样率会把它清零，靠 BSP 补回来。** `es8311_close()` 内部走 `es8311_suspend()`，
  把 DAC 音量寄存器写成 `0x00`，而 `es8311_open()` 不恢复它——也就是说每切一次
  采样率都会静音，**而且不报错**（PCM 写进去了、功放也开着，就是没声音）。
  `bsp_audio_set_fs()` 在 `open` 之后补一句 `bsp_audio_volume_set(s_volume)`，
  所以这条路是安全的；改那一段时**不要把这一句删掉**。
- **开机第一次出声时，硬件上的值和滑条上显示的不是一个数**：`bsp_audio_init()`
  是按 BSP 自己的默认值（`BSP_AUDIO_DEFAULT_VOLUME` = 93）打开 codec 的，而
  app_audio 存着的是 50。以前的做法等于"等你哪天动了滑条再同步"，症状是
  **开机直接去按快门，那一声比音乐还响，而设置页上写着 50**。现在 `app_sound`
  在播放前会把 app_audio 的当前值应用一遍，两边从第一次出声起就一致。

## 相册

主菜单 → **Files** 进入相册：列出 `/sdcard/PHOTO` 下所有 `.jpg`，新的在前，3 列缩略图网格。点缩略图进全屏大图，大图页的 **Email** 按钮把这张照片作为附件发出（multipart/mixed，base64，按 3KB 分块流式编码，不会把整个文件读进内存）。超过 18MB（`APP_MAIL_MAX_ATTACH`，见「音乐」一节里的推导）直接拒绝，不拿时间冒险。

标题栏右上角常驻一个 **`Delete`** 按钮：点它进入批量选择，再点缩略图切换选中（选中态是格子底色变强调色，颜色取自图片周围的边框区域，比加勾标更清楚也更省控件），标题栏变成「N selected」并出现 `All`（全选/全不选）；再点一次 `Delete` 弹二次确认。返回键在选择模式下是「取消选择」而不是退出页面。

同一个按钮承担"进入"和"确认"两个角色，靠 `s_select_mode` 区分。**最初做的是长按缩略图进入，实测手感不好**——要按住 400ms，而且网格是滚动区，长按和拖动容易混在一起，所以改成了按钮。

二次确认框的回调里**必须用 `lv_event_get_current_target()`，不能用 `lv_event_get_target()`**。msgbox 的按钮是 btnmatrix，它发的 `VALUE_CHANGED` 会**冒泡**到 msgbox 才轮到回调；冒泡时 LVGL 只往上挪 `current_target`，`e->target` 始终是最初发出事件的对象（那个 btnmatrix）。用 `get_target` 拿到 btnmatrix 却被当成 `lv_msgbox_t` 去读 `btnm` 成员，得到野指针后解引用，直接 `LoadProhibited` 复位。**设置页的 `Reset Wi-Fi` / `Reset Email` 原来也有同样的写法，一并修了。**

删除后是**重新扫描整个目录并重建网格**，不是从内存数组里剔除：万一某张删失败（只读、FAT 出问题），重扫能一次把状态对齐，也免得索引失效。重建时先删控件再释放解码缓冲——反过来的话 `lv_img` 会短暂拿着已释放的指针。

缩略图是按需解码的：定时器每拍解一张，用 `esp_jpeg` 解到 80×60，解好一张挂一张，所以网格是从左上往右下逐渐填满，而不是卡住好几秒再一起出现。解码跑在 LVGL 任务里，代价是加载期间界面略卡，换来的是完全不用处理"解码任务比页面活得久"那一类竞态。

**解码档位是按源图现挑的，不能写死**：卡里会同时有升级前的 QVGA(320×240) 和升级后的 VGA(640×480) 照片。写死 1/4 的话 VGA 照片的缩略图是 160×120，塞不进 97×73 的格子；写死 1/8 的话旧 QVGA 照片只有 40×30，小得看不清。`jpeg_load()` 先用 `esp_jpeg_get_image_info()` 拿源图真实尺寸（这个值直接读 SOF0，不受 `out_scale` 影响），再挑"结果不超过目标"的最大档位。大图同理，解到不超过屏幕的 320×240。

需要自己解码的原因是 **LVGL 8.3 读不了标准 JPEG**：`CONFIG_LV_USE_SJPG` 没开，而且它那个 SJPG 是自定义的分片格式，本来也不认普通 `.jpg`。

## 音乐

主菜单 → **Music** 进列表：`/sdcard/MUSIC` 下的 `.mp3`（后缀大小写不敏感）按文件名升序排，点一首就开始放并**进入大图模式**；底部常驻一条"正在播放"，点它也能进大图模式，三个按钮是上一首 / 播放暂停 / 下一首。

**一首放完自动接下一首**，最后一个放完就停（不绕回第一首——按"下一首"按钮才是绕回的）。2026-09-22 之前这条**从来没生效过**：`play_file()` 只在"按了切歌按钮"那条路上给 `*next_out` 赋值，自然放完时它还是调用方初始化的 `-1`，`run_playback()` 就当成"播放列表放完了"直接收摊。界面看着一切正常（进度条走到头、状态回到 IDLE），只是不放第二首。修法见 `play_file()` 结尾那段注释。

**大图模式**：左边一张旋转的黑胶唱片（纯 LVGL 图元画的，不需要素材），右边一根**竖排音量条**，下面是进度条、左右时间、上一首/播放暂停/下一首。歌名在标题栏上。

唱片是**红黑配色**（2026-09-22 从蓝黑改过来，原来中心纸标用的是主题那个 iOS 蓝）。几个决定：盘面用**近黑带红调**而不是纯黑（红纹路要和它同族，纯黑上像"贴了几道红胶带"）；外圈加一道深红描边让轮廓在任何背景上都成立；**中心孔用盘面色而不是屏幕底色**——原来开的是浅灰的洞，那是"红色圆环中间有个洞"，换成盘面色才是唱片"中间那个孔"，纸标因此变成一个红环；高光弧（转起来的那道）沿用主题里的 `UI_COLOR_DANGER`。

改配色全部集中在 `page_music.c` 的 `build_vinyl()`，5 个色值都是那一段顶上的宏（`VINYL_DISC` / `VINYL_RIM` / `VINYL_GROOVE` / `VINYL_LABEL` / `VINYL_HILIGHT`）。旋转仍然只改 `lv_arc` 自带的 `rotation`，不走 `transform_angle`——后者每帧要把整块区域重新渲染一遍。

**标题栏右侧两个常驻按钮**，和相册页一套做法：

- **信封** —— 进批量选择，把选中的曲目作为附件发一封邮件（附件标成 `audio/mpeg`）；
- **垃圾桶** —— 进批量选择，删除选中的文件。

进选择模式后标题变成「N selected」并出现 `All`/`None`（一个按钮兼全选和全不选），返回键变成"取消选择"。**删除前会先停播**——FATFS 上删一个正被 `fopen` 打开的文件（就是正在播的那首）行为不可靠，而且列表重建之后 `s_index` 会指向别的歌，停播比"保住播放"简单得多。

进度和时间按 **200ms 的 LVGL 定时器**刷，解码任务只负责出声，不碰界面。

几个实现上的取舍：

- **中文文件名用专门的字体**。界面文案一律英文是因为 LVGL 内置字体没有汉字，而歌名是中文的，所以列表/正在播放条/大图模式标题都显式换成 `UI_FONT_CJK`：**GB2312 一级字库（3755 汉字）+ 符号区 + ASCII + 常用中文标点**，共 4562 字形约 710KB flash，由 `tools/gen_cjk_font.py` 从立创官方例程自带的阿里巴巴普惠体里切出来（**改了要重跑脚本**）。二级字库（那 3008 个生僻字）**装不下**——`lv_font_fmt_txt_glyph_dsc_t` 的 `bitmap_index` 只有 20 位、位图上限 1MB，一级加二级实测 1.25MB 直接越界；真要补得再生成一个字体用 `lv_font_t.fallback` 串起来。一级字库覆盖日常文本约 99.7%。上一版用 LVGL 自带的 `lv_font_simsun_16_cjk` 只有 1166 个常用字，中文歌名实测**约一半是方框**，别再用它。
- **进度条可以拖动跳转**，按"目标时间占总时长的比例"换算成文件里的字节位置。CBR 准确，VBR 是近似值（没解析 Xing 的 TOC）。时长优先取 Xing/Info 头里的总帧数，没有这个头才按码率估算。
- **默认音量 50**。0dB 大约在 93 附近（见 `lckfb_bsp.h` 的音量注释），所以这一档约 -21dB，留了足够余量。**原来实测音量 60~70 时高音部分就开始破音**（喇叭/功放的过载失真，不是解码问题），所以默认值压得低。**换喇叭（2828 4Ω 3W）之后这条还没重新量过**——用户反馈听歌没有噪音了，觉得可以调响就往上调，默认值暂时没动。**93 以上一律是数字增益（0dBFS 在 93，100 = +3.6dB）**，那一段与喇叭无关，`bsp_audio_volume_set()` 会夹住。
- **音量不走命令队列**，界面线程直接写 I2C。滑条一拖就是几十上百个事件，队列只有 6 格，丢几个就会出现"手停下来了音量还在中间"。
- **发 MP3 比发照片更容易撞上限**：单封邮件的附件总量上限是 **18MB**（`APP_MAIL_MAX_ATTACH`）。这个数是按收件方算的——Gmail 等普遍限制整封邮件 25MB，而附件 base64 后要膨胀 4/3，18MB 编码完约 24MB，再往上加就是「整封传完才被拒」。选中的文件超了会先算总大小并给出「Too big: X MB」，不会连上服务器白跑一趟。**传 18MB 要一两分钟**，期间显示 `Sending...` 是正常的。

歌词功能做过一版又移除了（连同编码识别、GB2312 码表、解析器），代码和结论都没留——
档案 2026-09-26 清掉了，要翻只能从 git 历史里找。

### 采样率与那条存疑的注释

卡里的 MP3 采样率各不相同（44.1k / 48k / 22.05k / 16k…），播放时**按文件自己的采样率重配 I2S**，做法和立创官方例程 `11-mp3_player` 的 `bsp_codec_set_fs()` 一致：每个文件 `esp_codec_dev_close()` + `esp_codec_dev_open()`。

`components/lckfb_bsp/lckfb_bsp.c` 里以前有一段注释断言"这么切会让 ES8311 的时钟分频器停在旧值"，那是**推理出来的结论，没有实测过**，现在改成实测：`esp_codec_dev_open()` 之后回读 ES8311 的 REG02~REG08，和该采样率的期望值比对，不一致就补写并打 `ESP_LOGW`。

之所以要盯这一眼，是因为：

- **MCLK = 256 × fs 时，48k / 44.1k / 32k / 24k / 22.05k 写进那 7 个寄存器的是完全相同的字节**（`coeff_div[]` 里这些行的分频系数都一样，只有 OSR 随采样率变，而 ≥22.05kHz 都是同一个值）。也就是说例程就算真的切了采样率，也很可能什么都没写；
- 例程自带的那三个演示 MP3（`11-mp3_player/spiffs/`）**全都是 48000Hz**，正好等于它的开机默认值——它跑自己的素材时采样率从头到尾一次都没变过。

本工程默认 16000，点第一首 44.1kHz 的歌就要跨过 OSR 那条边界。所以：

- **串口里没有那条警告** → 那几个写本来就是生效的，以前那条结论是错的；
- **有警告** → 疑点是真的，代码已经顺手补上了。

**2026-09-20 实测的答案是前者**：

```
I (31990) bsp: 16000 Hz：ES8311 时钟寄存器校验通过（7 个全部符合预期）
I (32120) bsp: 44100 Hz：ES8311 时钟寄存器校验通过（7 个全部符合预期）
```

第一次从 16k 跨到 44.1k（OSR 要从 0x20 变成 0x10）时，回读到的寄存器**已经是正确值**——esp_codec_dev 那几个"在复位态写的"寄存器照样写进去了，**老注释里那条结论是错的**。所以那段校验代码现在只是纯观测：正常情况下它一个字节都不写，只花 7 次单字节 I2C 读（约 1ms）。**留着它是有价值的**：万一以后换 IDF 或换 codec 驱动版本，这条日志能第一时间把同类问题指出来。

### 相机和音乐只能跑一个

这条不只是产品选择：相机一帧 614400 字节走 PSRAM，但音频缓冲必须在内部 RAM，两者抢的是同一块稀缺资源（实测相机 + WiFi + LVGL 都跑着时，一个 96KB 的 DMA 分配会直接失败）；而且两者都是 CPU 密集型，出口（I2S → ES8311 → 功放）也是共用的。

**这条规矩 2026-09-24 换了落点：音乐现在是"模式"，不是"页面"。** 加了 WS2812
氛围灯模块之后，原来的"离开音乐页就停播"站不住了——屏幕同一时刻只有一个页面，
进了 LED 页音乐就没了，频谱灯永远收不到输入。所以：

- **离开音乐页不再停播**（返回键和 `page_music_destroy()` 都走 `maybe_stop_audio()`），
  和副屏、和灯本身一样"跟模式不跟页面"；
- 落点挪到了**相机页**：`page_camera_create()` 里发现音乐还在放就先 `app_audio_stop()`
  （它关功放、释放解码器），U 盘模式本来就会停；
- 例外只有一个：`app_led2812_needs_audio()` 为真（频谱灯正拿音乐当输入）时不停。
  要让音乐停下来，去 LED 页那条迷你播放条上按暂停，或者回音乐页暂停。

副作用是自洽的：音乐一停（暂停、放完、被相机打断）PCM 就断，频谱柱子自己衰减到
全黑，那边不需要任何额外处理。

> **喇叭于 2026-09-22 换成了 2828 4Ω 3W。** 下面这条是换之前那颗板载小喇叭的结论，
> 保留下来是因为它记录了当时是怎么定位的（而且换喇叭之后还没重新量过）：
> 音乐听起来偏闷、发薄**曾经**是喇叭的物理上限（3–5kHz 以上滚降），不是解码或功放的问题
> ——当初那次快门声就是栽在这上面（见"拍照 → 快门声"一节）。
> 用户反馈换完之后"听歌没有噪音了"，所以**过载破音那条上限很可能已经不存在了**；
> 但音量 93 以上是数字增益（硬削顶）那条与喇叭无关，仍然成立。

## U 盘模式（把 TF 卡当读卡器）

主菜单 → **Work Mode** → **`USB Drive`** → 弹出一个模式页，同时**电脑上多出一个盘符**；在电脑上拷贝完、**安全弹出**之后，点模式页的 **Exit** 回到正常设备。

（这个入口 2026-09-22 从设置页的 STORAGE 分组搬到了工作模式页——它改的是整机形态而不是设置项，放设置页里得让人记得"往下翻"。）

**进去之后本机读不到卡了**：FATFS 已卸载，音乐页、相册页、设置里的 Free space 都会显示 `No TF card`。这是设计如此——同一张卡的 FAT 不能两边同时写。同理，**电脑还在写的时候点 Exit 会丢数据**，代码挡不住（我们没法强制电脑刷缓存），所以模式页上那句话是必须的：先在电脑上安全弹出。

### 和串口的关系（最容易被误会的一条）

板子只有**一个 Type-C**，后面挂了一颗 **CH334F 的 USB HUB**（原理图 `hardware/`），HUB 再分给两路：

```
Type-C ──> CH334F ──┬──> CH340K ──> UART0    (COM16：日志与烧录，走这条)
                    └──> ESP32-S3 原生 USB    (GPIO19/20，进模式时被 OTG 占用)
```

- **烧录和看日志不受影响**，因为走的是 CH340 那一路，不经过 ESP32 的 USB PHY。实测：U 盘模式开着也能正常烧录，日志也一直是连续的。
- 被占掉的是**原生 USB 口**：它在模式期间从"USB-Serial-JTAG"变成"USB 大容量存储设备"，退出后恢复。
- `CONFIG_ESP_CONSOLE_SECONDARY_NONE=y` 关掉了 USB-Serial-JTAG 那个**第二控制台**——它和 TinyUSB 抢同一个 PHY，留着只会让上面这件事多一层说不清。

**为什么必须手动开关，不能"插上就自动变 U 盘"**：那个 HUB 让原生 USB 只要插着线就一直连着，而板子靠这根线供电——"插上就自动"等于"开发时音乐相册全废"，而且从电脑角度看是磁盘被反复拔插。

### 内部顺序（顺序错了会毁 FAT）

进模式：停相机和播放 → **卸 FATFS** → **重建卡** → 建 MSC 存储 → 装 TinyUSB。退出反着来。

两个不明显的地方：

- **卸载会把卡一起销毁**。IDF 的 `unmount_card_core()` 里有 `call_host_deinit(&card->host); free(card);`——SDMMC 主机被 deinit、卡结构体被 free。所以"卸载完把卡交给 TinyUSB"这条路走不通，只能在 `lckfb_bsp.c` 里单开一个 `bsp_sdcard_card_init()`：只做 host init + slot init + card init，不挂文件系统。
- **两套挂载不能并存**。官方例程是"MSC 存储层自己拥有 FATFS"（开机建一次，用 `set_storage_mount_point()` 在应用和电脑之间切），而本工程的 `app_storage` 一直是自己 `esp_vfs_fat_sdmmc_mount` 的。所以这里**只在进模式时创建 MSC 对象**，正常路径一行没动。

任何一步失败都会**把文件系统挂回去**再返回错误——绝不能停在"卡既没挂也没暴露"的中间态，那会让音乐、相册、剩余空间全部失效而用户只看到一句"进模式失败"。

> 日志里那条 `tusb_desc: String index (238) is out of bounds` 是**噪音**：Windows 在问微软自家的 OS 描述符字符串（索引 0xEE），我们没提供，设备照常枚举和读写。不要去追它。

## 外接模块（Modules）

模块口是板上仅剩的两根空脚 **GPIO10 / GPIO11**（别的都占了：`0` Boot、`1-2` I2C、
`3-9/15-18/46` 相机、`12-14/38/45` 音频、`19-20` USB、`21/47-48` TF、`39-42` LCD、
`43-44` UART0 控制台、`26-37` flash + PSRAM）。所以物理上只能**一次插一个**，
不存在"同时挂好几个模块"这个形态。

主菜单 → **Modules** 是一张清单，**型号由人来点**：

```
WS2812 Matrix      Running  >
Tracked Vehicle             >
Printer            Unsupported
```

点一行 = `app_module_select()` 把那两根脚交给对应驱动，然后进那个模块的控制页。
`Running` 就是"现在选的是它"，是个**软件状态**，不是检测出来的。

### 为什么不做自动识别

**固件完全不读那两根脚来判断插了什么**——没有下拉电阻约定、没有 ADC 分压、
没有"拔掉自动关"。

这么定是为了把复杂度按住：自动识别要模块侧配合（每根脚上一颗特定阻值的电阻）、
要固件去解释分压、还要处理"拔掉的瞬间引脚悬空"这种中间态；而模块口从头到尾
就两个脚、型号一共三种，**问人比问脚便宜**。

代价写在明处，页面上也是这么写的：**插拔模块之前先把当前模块关掉**
（控制页上的 `Disable`）。一根脚同一时刻只能是一个外设的。

"一次只跑一个"是**软件规则**，不是电气事实：界面不给同时选两个只是第一道闸，
真正的约束在 `app_module_select()` 里——每个驱动的 `enable()` 开头都会拿
`app_module_selected()` 校验"现在轮到我了吗"。

状态**只存 RAM，不写 NVS**，和副屏开关同一个理由：看不见效果的模式不能掉电
自恢复；而且这次插的可能是另一块模块，恢复上次的选择反而有害。

### 引脚的归属

| 谁 | 什么时候 |
| --- | --- |
| `app_module` | 空闲态：两脚都是**输入 + 内部上拉**（开机就是，`app_module_init()`） |
| 选中的那个驱动 | 借用；它的 deinit 末尾**必须**调 `app_module_port_idle()` |

`led_strip`/RMT 和 `uart_driver_delete()` **都不会替你还脚**。不还的话 GPIO10
会停在一根被推挽驱动的输出上，下次插上的是别的模块，那根线就是被硬顶着。
`port_idle()` 是**引脚卫生，不是检测**——它只看自己刚用过的脚，不推断插了什么。

### WS2812 氛围灯（8x8，DIN = GPIO10）

三个效果互斥，控制页顶上切：

- **Manual** `lv_colorwheel`（只调色相，mode 锁死）+ 竖排亮度条；
- **Spectrum** 8 根柱子，一列一个对数频段，低频在左；
- **Test** 每次只亮一颗，按 WS2812 灯带串行顺序从 1 到 64 循环，每颗约 100ms。
  用于检查灯珠顺序和连接。

**频谱的信号来自解码后的 PCM，不是麦克风。** 板和喇叭在同一台设备上，放歌时
麦克风听到的就是这把喇叭——音量和频率响应都是二手的，还容易啸叫；而
`app_audio` 的 `write_pcm()` 之前那个位置 PCM 就在手边，顺带省掉 ES7210 的
初始化和一路 I2S RX。代价是**只有本机在放歌时才有反应**。

链路：`app_audio_set_pcm_cb()` 的回调（跑在解码任务里，只做一次 L/R 合并 +
存环形缓冲，**必须立刻返回**）→ 效果任务取 512 点 → 去直流 + 汉宁窗 →
**手写 radix-2 FFT**（N=512 约 23k flops，32ms 一帧里占 1.5% 的核，没必要引
esp-dsp）→ 8 个对数频段（段内**取平均**，宽频段不该占优）→ log 压缩 →
快升慢落（一帧落 3 行）。

- **频段表随采样率重建**，不重采样：卡里的歌 16k/22.05k/44.1k/48k 都有，
  而频段是按 Hz 定的，binHz 跟着变一下就行。
- 频谱输入是解码后的 PCM，FFT 幅值未按窗长归一化；较低的灵敏度和噪声门
  用来避免普通歌曲的宽带底噪让整板常亮，强频段峰值仍会抬高柱子。

WS2812 的时序是**自己用 RMT 编码的，没引 `espressif/led_strip`**：它的作用就是
把 `strip_send()` 那几十行包一层，而本工程一贯不要这种薄封装（自己的 MP3 解码
循环同理）。少一个依赖就少一处版本要跟着 IDF 走的地方——led_strip 3.x 就要求
IDF 5.3+ 拆出来的 `esp_driver_rmt`，而本工程锁在 5.1.7。时序取 10MHz 分辨率，
T0H/T0L/T1H/T1L = 4/9/8/5 tick（0.4/0.9/0.8/0.5µs），全在 ±150ns 容差内。

一次刷新 64 颗 × 24bit = **1536 个 RMT 符号**，远超一颗通道 48 字的 RMT 内存。
不用自己按块切：新 RMT 驱动的非 DMA 路径是**乒乓补齐**的（`rmt_tx.c` 把内存劈成
两半、靠 TX_THRESH 中断续灌），整帧丢给 `rmt_transmit()` 就行——在 WS2812 的
数据流中间人为断开是没定义的。

两个必须自己写的（led_strip 也没有）：**整帧限流**（`LED_MAX_MA` 800mA，64 颗
满白不封顶是 3.8A）和 **gamma LUT**（不做的话滑条低半段像坏的、色相过渡也难看）。

灯板坐标按**逐列顺序**映射：第 1 列从底部向上对应灯号 1–8，第 2 列从底部向上对应
灯号 9–16，依此类推；列与列之间不做蛇形反向。因此频谱柱从底部向上增长时，会按灯珠
编号逐列对应。

⚠️ WS2812 是 5V 供电的，VIH ≈ 0.7×VDD = 3.5V，而 S3 的 GPIO 只有 3.3V——短线上
通常能亮，但**属于规格外**。模块能接 3V3 供电就接 3V3，最省事。

### 履带车（UART 配网 + UDP 无线驱动）

**这一节讲的是主机这一半**（摇杆、链接状态、二维码）。车那一半——ESP32-C2 上的
差速电机、UART 行解析、网页遥控——在**另一个仓库**
[40chen/ESP32C2_tank](https://github.com/40chen/ESP32C2_tank)（本地就是
`../ESP32C2_tank/`），用 `pio run -t upload` 单独烧，不进这个仓库的构建。
下面这张协议表是两边的接缝，**改一边必须同时改另一边**。

**两根线只用来配网，之后车就跑开了。** 这是这一节最重要的一句话：

```
 ① 插上线：UART1（GPIO10/11，115200 8N1）
    Ecam 把 WiFi 凭据交给车 → 车连上 → 把 IP 报回来
 ② 拔掉线：之后走 UDP 单播（端口 3333）
    Ecam ──20Hz 摇杆包──→ 车
    Ecam ←─1Hz #ip 心跳── 车
```

所以以前那种"插着线才能开"的形态结束了：车被拎到屋子另一头照样开。
（代价见下面"单播的代价"。）

协议是**同一套纯文本行，只是跑在两个传输上**，两边各一个 `handle_line`：

| 方向 | 行 | 走哪条 |
| --- | --- | --- |
| Ecam → C2 | `x<f> y<f>\n` | 两条都走（知道 IP 就 UDP，否则 UART） |
| Ecam → C2 | `#hi` | UART |
| C2 → Ecam | `#ok v1 tank` | UART（不答 = 旧固件，不推凭据） |
| Ecam → C2 | `#wifi 1 <b64 SSID>` / `#wifi 2 <b64 PASS>` / `#wifi 3` | **只走 UART**，事务式，第三行才写 NVS |
| C2 → Ecam | `#wifi ok` / `#wifi err <code>` | UART |
| C2 → Ecam | `#ip <addr>` | UART 在拿到 IP 时及收到 `#hi` 时报告；之后**每秒一条当 UDP 心跳** |

- **发哪条路**：知道车的 IP 就走 UDP，否则走那根线。两条路不会同时发。
  有线兜底不是只在没配网时有用——IP 记错了、车换了地址还没重新插线时，
  线一连上就能继续开。
- **丢链就把向量归零**让车停住。界面上的"没响应"窗口是 **1500ms**（车的
  心跳是 1Hz，500ms 会把正常心跳也判成掉线）；而**真正让车停下来的是车上
  那个 500ms 看门狗**——两个数故意不一样：一个是"用户看得对不对"，
  一个是"车该不该停"。
- **UDP 上不接受 `#wifi`**（车那边直接回 `#wifi err 4`）。局域网里任何人
  打一行就能改掉车的配网，这个口子不该开。摇杆指令无所谓——网页遥控本来
  就是无鉴权的，用户已经接受了。
- **退出顺序不能动**：停任务 → **补发 3 条停车指令** → 拆 UART + 关 socket → 还脚。
  任务一停就没人发了，车要等 500ms 看门狗才自己停，这半秒车是照最后一条
  向量跑的。
- `#` 前缀是刻意的：**不认识的行必须无害**。没升级的 C2 撞上它走
  `sscanf("%c%f")` 的 Unknown 分支，动都不动；payload 用 base64 是为了
  凭据里的空格和中文 SSID 不会把"按空白分列"的协议撑破。
- ⚠️ **凭据是 base64 明文过两根线的**。base64 是编码不是加密，模块口上谁都能读。
  无线那段也没有加密（UDP 明文）。本地用可以，但别以为它是安全的。

#### 单播的代价（写在明处）

车的 IP 只有 UART 能告诉 Ecam，而 UDP 是**单播**，所以：

**车重启后如果 DHCP 给了它新地址，就得重新插一次线。**

为什么不做广播（那就不用管 IP 了）：同一局域网里两辆车会一起动；也不做
"车定期广播自己、Ecam 记下来"那套发现机制——为了省掉"偶尔插一次线"引入
两边的发现逻辑，不值。真嫌烦的时候再加，改动只在 `app_tank.c` 的
`udp_send_vector()` 里换个目标地址。

#### 页面上那个二维码

履带车页的 **Address** 行是可点的，点开是一张二维码：

```
    ┌──────────┐
    │ ▄▄▄ ▄ ▄▄ │   手机扫一下 → 打开车的网页遥控
    │ █ █▀▀█ █ │
    │ █▄▄▄▄▄█ │   tap anywhere to close
    └──────────┘
     http://192.168.1.23/
```

- 让用户拿手指在 320×240 的屏上敲 `192.168.x.x` 是最容易出错的环节，
  错一位就是"打不开"，还得回来重看。
- 二维码用 `espressif/qrcode`（里面是 Nayuki 的 qrcodegen）。**不自己写**：
  Reed-Solomon + 掩码那套写错了的表现是"图能画出来、手机扫不出来"，最难查。
- 点阵是**自己填的一块 RGB565 缓冲**（`lv_img` + `LV_IMG_CF_TRUE_COLOR`，
  和相机预览一个路子），不走 `lv_canvas`。四周的静默区**由卡片的留白充当**，
  不画进点阵里——所以缓冲只有 150×150×2 = 45KB，放 PSRAM。
- 扫不出来的话先看模块数：`esp_qrcode_get_size()` 给的边长的平方才是真正的
  采样密度，`QR_MAX_PX / n` 那个 `scale` 最小夹到 3px——再小就该改大
  `QR_MAX_PX` 或者把地址弄短点了。

### 自动翻转（QMI8658）

设置页 → DISPLAY → **Auto Rotate**（默认开，**存 NVS**——它是"填一次就不动"的
偏好，不像工作模式页那几项刻意不落盘）。

判方向用**加速度计**，不用陀螺仪：陀螺仪是角速度，积分出来会漂，"哪边是上"
本来就是加速度计的活。

**判据是"和参考方向的夹角"，不是某一根轴**——这一版改过，第一版硬编码了一根轴
（`IMU_FLIP_AXIS`），上板发现根本不动：**哪根轴朝上取决于芯片在板上的贴装方向**，
在板子外面定不了。现在改成：

- **参考方向** = 最近一段时间的重力方向（**自适应**，见下）；
- **夹角 ≤ 60°** → 正立；**夹角 ≥ 120°** → 倒置（= 和参考的反方向夹角 ≤ 60°）；
- **中间那 60° 是灰区，保持现状**——迟滞带：从正立翻到倒置，手必然扫过这一段，
  在那里不改变状态，所以姿态抖动不会让画面来回跳；
- 真改变状态要**连续 4 拍一致**（20Hz 下 200ms），放在桌上轻碰一下不会翻。

60° 和 120° 是同一对余弦（±0.5），代码里只有一个 `IMU_CONE_DEG`。
这样**和贴装方向彻底无关**，也不用再让人去试一个常量。

**参考方向必须自适应，这是上板踩出来的**：第一版把参考定在"打开开关那一刻"，
结果实测参考是 `(0.08, 0.11, 0.99)`——Z 轴占绝对多数，也就是**采参考时设备
平放在桌上**。而平放时重力沿着屏幕法线，用户在平面里转 180° 重力方向根本没变，
夹角永远是 0°，永远够不到倒置门限。表现就是"自动旋转没用"。

现在参考以约 10 秒的时间常数跟着当前姿态走（`IMU_REF_ADAPT_ALPHA`，20Hz 下
0.005）：开机时不管摆成什么样，拿起来正常用一两秒，参考就对齐到"手持正立"，
之后翻转立刻判得出来（真翻转只要 0.5 秒，参考几乎没动）。**判成倒置期间冻结
自适应**——否则用户一直倒着拿，参考也跟着倒过去，界面会自己翻回来。

**参考没对齐时有个可用的救急手段**：设置页把 Auto Rotate 关一下再打开——
`app_imu_set_enabled(true)` 会用**当前姿态**重新起一个参考（`s_ref_req`）。
所以"想让它把这个姿态当成正立"就是重开一次开关，不用等那十秒。

### ⚠️ 陀螺仪那条路删掉了（2026-09-25），以及为什么

原来这里有一套"两条判据"：某根轴的 `|a| > 0.85`（重力几乎沿着那根轴）就认为
加速度计进了盲区，改把那根轴的**角速度积分**起来，转够 150° 当翻了一次。

**那个说法只对了一半，而错的那半正好把用户实际在做的动作挡在外面。**
盲区的准确条件是"**旋转轴和重力平行**"，不是"重力沿着某根轴"；代码只能看到
后者，就拿它当了代理判据。上板实测（用户报的两个姿态，也正是他要的两个）：

| | 轴向量 | 重力沿 |
| --- | --- | --- |
| 正立 | `+0.99 +0.01 -0.16` | +X |
| 倒置 | `-0.92 +0.10 +0.39` | −X |

他是**绕 Y 轴滚 180°** 在这两个之间翻的——重力方向从 +X 跑到了 −X，加速度计
看得一清二楚。但 `|ax| > 0.85` 先把这一拍踢给了陀螺仪，而陀螺仪读的是
`dps[normal_axis]` = **X 轴**角速度，正好是和重力平行的、这次转动里几乎为零的
那根轴。日志里就是 `转角累计 +0°`，屏幕纹丝不动。

用户要的就是"这两个姿态各自 ±60° 以内定死正/反"，那本来就是夹角判据的事。
删掉之后只剩一条路，也不再有"两条路互相打架"的问题。

**代价（明确接受）**：设备**平放**在桌上绕竖直轴转 180° 不再翻屏。那种转法重力
方向一个数都不变，加速度计物理上测不出来（平放时屏幕朝上，也没人在看方向）。

顺带记一条**仍然有效**的教训：`CTRL7 = 0x03` 只是打开陀螺仪的**使能位**，采样率
在 `CTRL3` 里，漏写它陀螺仪根本不采样（现在不读陀螺仪了，但 CTRL3 照写，
CTRL7 那两个 bit 也照开——这是上板验过的配置，不为了省电去动它）。

⚠️ **排查"翻转不灵"先看屏幕上那一行**：设置页 → DISPLAY → Auto Rotate
右边的值会实时显示状态（一秒刷新一次）：

| 显示 | 含义 |
| --- | --- |
| `No sensor` | 自检没过（0x6a / 0x6b 都没应答），翻转功能是关着的 |
| `Off` | 传感器在，但开关关着 |
| `On` | 传感器在、开着、当前判成正立 |
| `Upside down` | 传感器在、开着、当前判成倒置 |

把设备翻过来盯着这一行看：从 `On` 变成 `Upside down` 就是判对了。
**这一行是刻意做的**——串口日志在有些机器上不好看（这台就是这样），
把状态搬到屏幕上，用户不用连串口也能说出"它说 No sensor"还是"它说 On 但没反应"，
而这两种情况要修的地方完全不同。

串口那边也有：开机 15 秒内每秒打一行，长这样——

```
I (145092) imu: 轴 +0.97 +0.02 -0.22  夹角  12°  正立区  → 画面正立
I (168642) imu: 轴 -0.92 +0.10 +0.39  夹角 166°  倒置区  → 画面倒置
I (120000) imu: 轴 -0.39 +0.12 +0.91  夹角  97°  灰区    → 画面正立
```

**夹角**是当前重力方向和参考方向的夹角，后面跟它落在哪个区。两个门限是
60° 和 120°，**灰区那一档必须认识**——用户照着这行问"我都快翻过来了怎么没
反应"，答案往往就是夹角还没到 120°。

15 秒之后只在**姿态动过了**才打（一秒一行、相对上一行位移超过
`IMU_AXIS_LOG_MOVE`），所以"拿起来转一下"永远有数据，放着不动就一直安静，
不用重烧固件去开 DEBUG。判定翻转那一刻单独打一行（`方向翻转 → 正立/倒置`）。

**如果三根轴一直是 0**，说明 IMU 没读到数据；**如果夹角一直贴在 0° 附近不动**，
说明参考还没跟上来（拿在手里等十秒它自己会跟）。

**要立刻重采参考**：设置页把 Auto Rotate 关一下再打开，它会用当前姿态重新
起一个参考，不用等那十秒。

翻转只做 **0°/180°**：面板 MADCTL 的 MX/MY 同时取反，触摸芯片单独告诉一遍
（`esp_lcd_touch_set_mirror_x/y`）——**FT6336 是另一颗芯片，面板翻它不会跟着翻**，
否则画面对着、手指按在镜像的位置上。
**LVGL 画布仍然是 320x240，六个页面一行都不用改**。90/270 不做：那会把画布变成
240x320，而主菜单 94px 的格子、副屏 130/166 的栏宽、相册三列全是按 320 宽算死的。

⚠️ **只翻 MADCTL 是不够的，必须同时让 LVGL 整屏重画**（2026-09-25 踩过）。
MADCTL 管的是"写进来的像素落到 GRAM 的哪个地址"，不是"屏幕上怎么扫"——所以
只改 MX/MY 的话，**已经显示着的那一屏一个像素都不会动**，看上去就是"翻转没生效"。
当时 `bsp_lvgl_set_flip()` 里直接调 `esp_lcd_panel_mirror()`，日志打了
`画面翻转 180°`、SPI 也没报错，屏幕就是不动，根因就在这。

正确做法是 `lv_disp_set_rotation(disp, upside_down ? LV_DISP_ROT_180 : LV_DISP_ROT_NONE)`：
`lv_disp_drv_update()` 的结尾依次做了整屏失效 + 全树 layout 失效 + 调
`drv_update_cb`，而 esp_lvgl_port 的 `drv_update_cb` 会按 `disp_cfg.rotation`
（= `swap_xy/mirror_x/mirror_y = true/true/false`，必须和 `lcd_panel_init()` 里那组
一致）算出 `(!mirror_x, !mirror_y)` 写进 MADCTL——**一次调用把"改寄存器"和
"重画"都做了**。

顺带纠正一句早期的错判：**这里不会变成软件旋转**。LVGL 只在 `sw_rotate` 置位时
才做软件旋转（`lv_refr.c:1298`），而 esp_lvgl_port 从不设这个标志——所以
`driver->rotated` 在这里**只**驱动 MADCTL，没有每帧整屏重绘的开销。
（这句话之前在 README 里写反了，是照着"配了 rotation 就是软件旋转"想当然写的。）

**模块页上那个 `Turn off` / `Disable module` 关的是什么**：是**模块本身**，不是
页面。返回键只是走人——灯照亮、链路照连（跟模式不跟页面，同副屏那条）。
第一版这个按钮只写 `Disable`，含糊到用户要问"这是什么功能"，所以现在两个页面
都改了名，LED 页底部还补了一行说明。这一格只有 92px 宽，
`Disable module`（14 号字量出来 111.8px）放不下，所以那里用 `Turn off`。

**I2C 冲突那个疑点可以排除**：QMI8658 @0x6a 和 PCA9557 @0x19、ES8311 @0x18、
FT6336、相机 SCCB 都挂在同一条 I2C0 上，地址不撞；而且参考项目
`for_example/LCSZP_handheld` 就是**在同一条总线上同时用 PCA9557 和 QMI8658** 的
（同一颗 S3、同一套旧版 `driver/i2c.h` 接口），它跑得通。之前"没有数据"更可能的
原因是本工程从来没初始化过它（grep 全工程只有注释），其次是地址或 400kHz 时序。
所以 `app_imu_init()` **第一步是自检**：0x6a 读 `WHO_AM_I`（期望 0x05），不通就
自动再试 0x6b，把结果打进串口——"读不到"能一眼看到是哪一层，而不是屏幕上"转了
但没反应"。自检不过只是关掉翻转，不影响别的功能。

⚠️ **`IMU_FLIP_AXIS` 要上板确认**：哪根轴在画面正立时指向上方，和芯片贴的方向
有关。默认按参考工程用 Y；判定不对就把设备翻过来，看串口里三根轴哪个从 +1 变到
−1，改一个常量了事。

3.2 拍照功能
功能描述：用户可通过屏幕取景，按下 Boot 键触发拍照。

技术要点：

摄像头驱动：使用 ESP-IDF esp32-camera 组件。

GC0308 配置为 RGB565 输出，匹配屏幕预览。

初始化时注意 I2C 总线复用。

预览画面全屏显示在 320×240 屏幕上。

顶部状态栏显示 WiFi、TF 卡、电量等状态。

底部控制栏半透明黑色背景，居中放置圆形快门按钮。

3.3 照片存储功能（TF 卡）
功能描述：拍摄的照片以 JPEG 格式自动存储到 TF 卡中，文件名包含时间戳。

技术要点：

TF 卡挂载：使用 SDMMC 1-SD 模式挂载到 /sdcard。

仅支持 FAT32。32GB 以上卡若为 exFAT，需用户手动格式化。

文件命名：IMG_YYYYMMDD_HHMMSS.jpg。

时间戳通过 NTP 服务器同步获取。

GC0308 不直接输出 JPEG，实际流程为：

抓取 RGB565 帧
软件 JPEG 编码
写入 TF 卡照片目录
照片目录建议：/sdcard/PHOTO。

拍照时 UI 给出“保存中”反馈，避免用户重复按键。

3.4 照片浏览与邮件发送
功能描述：用户可通过触摸屏浏览 TF 卡中的照片，并选取照片通过 WiFi 以邮件附件形式发送。

技术要点：

照片浏览页使用缩略图网格，如 3 列布局，圆角裁切。

点击缩略图进入大图预览。

大图预览页提供“发送邮件”按钮。

若尚未绑定邮箱，提示先进入设置页绑定。

WiFi 连接：使用 esp_wifi 组件，STA 模式连接路由器。

邮件发送：使用轻量级 SMTP 客户端。

Gmail 必须使用 16 位应用专用密码，而非账号密码。

附件读取：从 TF 卡读取 JPEG 文件，加入 MIME 附件结构。

邮件配置存储在 NVS：

WiFi SSID / 密码

SMTP 服务器地址

发件邮箱

应用专用密码

收件邮箱

支持“重置邮箱 / WiFi”选项。

3.5 音乐播放功能
功能描述：用户可浏览 TF 卡中的音乐文件，并通过 ES8311 播放。

技术要点：

音乐目录建议：/sdcard/MUSIC。

支持格式：优先支持 MP3，可扩展 WAV。

文件扫描：启动音乐页时扫描 TF 卡音乐目录，生成播放列表。

解码方案：

使用 ESP-ADF 的 MP3 解码器，或

使用轻量级 Helix MP3 解码库。

音频输出：ES8311 通过 I2S 输出。

播放控制：

播放 / 暂停

上一首 / 下一首

音量加减

进度条显示

音频缓冲区使用 heap_caps_malloc(..., MALLOC_CAP_SPIRAM) 分配，避免耗尽内部 RAM。

播放时注意与 LVGL、摄像头、WiFi 的资源竞争。

3.6 触摸屏配置输入功能
功能描述：用户通过触摸屏软键盘输入 WiFi 密码和邮箱账号信息，无需串口配置。

技术要点：

UI 组件：LVGL lv_keyboard。

输入流程：

用户在设置页点击“WiFi 设置”或“邮箱设置”。
弹出输入界面，显示当前配置项和软键盘。
用户输入完成后点击“保存”。
数据写入 NVS。
WiFi 密码输入可显示或隐藏，邮箱账号正常显示。

首次启动或 NVS 为空时，引导用户进入配置流程。

支持重置 WiFi / 邮箱配置。

3.7 Type-C 读卡器模式
功能描述：通过 Type-C 接口将设备模拟为 U 盘，让电脑读取 TF 卡中的照片和音乐。

技术要点：

ESP32-S3 使用 TinyUSB 实现 USB MSC 设备。

进入读卡器模式前：

停止相机预览、音乐播放、WiFi 等任务。
sync 文件系统。
卸载 TF 卡。
将 TF 卡作为 USB MSC 存储介质暴露给电脑。
退出读卡器模式后：

停止 USB MSC。
重新挂载 TF 卡到 /sdcard。
恢复 UI 和相机功能。
注意：USB-Serial-JTAG 与 TinyUSB 共用 GPIO19/20，烧录/日志/读卡器模式不能同时使用。

传输速度受 1-SD 模式和 TinyUSB 限制，适合照片、音乐等中小文件读取。
