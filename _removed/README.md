## 歌词显示（2026-09-20 移除）

音乐大图模式里**滚动显示同步歌词**：读 MP3 同名的 `.lrc`，按播放位置高亮当前行、
自动滚到视野里；没有 `.lrc` 就放那张旋转黑胶，点视觉区可以在两者之间切。

### 这里有什么

| 文件 | 是什么 |
| --- | --- |
| `main_app/app_lyrics.c` / `.h` | `.lrc` 查找、编码识别、解析、按时间查行 |
| `main_app/gb2312_table.c` / `.h` | GB2312 → Unicode 查表（87×94 区位直查，约 16KB flash） |
| `tools/gen_gb2312_table.py` | 生成上面那张表的脚本（用 Python 自带的 gb2312 codec） |

### 为什么移除

**用户决定不用这个功能了**（2026-09-20）。功能本身是通的：解析器在电脑上验过
（UTF-8 / BOM / 双 BOM / GBK / 只有标签 / 空文件 / 乱序时间戳 / 三位小数 /
501 行超限 / GBK 扩展字 / 截断在半个字上，外加 300 个随机输入不崩），设备上的
路径也对——日志里能打出 `没有歌词文件：/sdcard/MUSIC/李白-李荣浩.lrc`，
说明"MP3 同名换后缀"这条推导是准的。但卡里始终没有放过 `.lrc`，而且用户明确
表示不做歌词了，所以整块移走，大图模式只留黑胶。

### 如果以后要重做，这几条别再试一遍

1. **LVGL 8.3 的事件不会自动冒泡**：`lv_event.c` 的 `event_is_bubbled()` 只对
   `CHILD_CREATED` / `CHILD_DELETED` 恒返回 true，其余（含 `CLICKED`）都要求
   当前目标对象带 `LV_OBJ_FLAG_EVENT_BUBBLE`。而 `lv_obj_create()` 默认带
   `LV_OBJ_FLAG_CLICKABLE`、命中测试取最内层可点对象——所以"把回调挂在父容器上
   等着收子对象的点击"**会一声不响地完全失效**。当初"点视觉区切歌词/黑胶"
   就是这么废掉的（没有报错、没有日志，看起来像没实现）。
   工程 README 里那条"msgbox 的 VALUE_CHANGED 会冒泡到 msgbox"记的是现象，
   真正原因是 `lv_msgbox.c` 自己给 btnmatrix 加了那个标志。

2. **编码识别按"BOM → 合法 UTF-8 → GB2312"的顺序判**，判据是 GB2312 汉字的
   两个高位字节在 UTF-8 里根本不合法。两个实测的坑：
   - **BOM 要用循环去掉**：见过编辑器在已经带 BOM 的文件上再加一个，剩下那个
     BOM 会顶在第一行最前面，让"行首是 `[` 才算歌词"的判断认不出这一行——
     症状是**第一句歌词无声消失**，很难往编码上想；
   - **GBK 的首字节范围是 0x81~0xFE、尾字节 0x40~0xFE**，查不到的字要**两个
     字节一起吃掉**，只吃首字节的话尾字节会当成 ASCII 漏到屏幕上（扩展字"髙"的
     尾字节是 0x7B，屏幕上就多出一个 `{`）。

3. **汉字字库覆盖是个真问题**：LVGL 自带的 `lv_font_simsun_16_cjk` 只有 1166 个
   常用字，实测**歌词和中文歌名约有一半显示成方框**。后来换成立创官方例程里那个
   阿里巴巴普惠体（切成 GB2312 一级字库子集，见 `tools/gen_cjk_font.py`）。
   重做歌词的话直接用那个字库，别再用 simsun。

4. **测试台可以复用**：临时目录里搭过一套主机测试（gcc + 桩头文件
   `esp_err.h`/`esp_log.h`/`strlcpy`，编译 `app_lyrics.c` + `gb2312_table.c`），
   比对着一行行读代码快得多，而且能覆盖上板试不到的畸形输入。

恰恰就是"电脑上听着正常、板子上听不见"。那两个脚本留着是因为它们记录的频段分析仍然有效。

### 为什么移除

**核心原因：素材的能量分布和这颗小喇叭的频率响应对不上。**

实测频谱（1024 点 DFT 的能量占比）：

```
             源素材    固件里最终那版
  0-  250Hz   0.0%       0.0%
250-  500Hz   0.1%      82.5%   ← 补了 body 之后
500- 1000Hz   0.5%       8.1%
1000-2000Hz   4.7%       1.4%
2000-4000Hz  25.2%       5.5%
4000-8000Hz  28.4%       2.5%
8000-22050Hz 41.2%        —
```

原素材 **1kHz 以下只有 1.6% 的能量，九成在 2kHz 以上**。板载小喇叭 3–5kHz 以上
就滚降了，等于绝大部分能量落在它放不出来的频段。

**对照实验印证了这一点**：`Settings → Test Speaker` 放 440Hz 正弦非常清楚
（能量全在喇叭谐振点上），而快门声走同一套代码、同一条通路却几乎听不见。

补了低中频的"身体"（`shutter-body-0.30`，1kHz 以下提到 60%）之后在板子上
**仍然偏小**。最后又试过一次**把用户重采样的 PCM 原样搬进固件、不做任何处理**
（峰值 -3.6 dBFS、RMS -23.9 dBFS，比测试音低 16dB），仍然是同样的结果，
于是决定整个功能不做。

### 如果以后要重做，这几条别再试一遍

1. **I2S 通道必须在 `bsp_audio_init()` 里 `i2s_channel_enable()`。**
   这一点已经修好并保留在 `components/lckfb_bsp/lckfb_bsp.c` 里了，**不要删**——
   MP3 功能也要靠它。当初移植时把这一句删掉了（注释里还写着理由，而理由是错的），
   结果是 I2S 主时钟起不来、`i2s_channel_write()` 一个字节都排不进 DMA，
   症状极像硬件故障：ES8311 寄存器全对、功放也开着，就是没声音。
   官方参考实现在 `O:\Desktop\DIY\ESP32 参考项目\11-mp3_player`。

2. **内部 DMA RAM 很紧张。** 实测相机 + WiFi + LVGL 都跑起来之后，
   `heap_caps_malloc(96000, MALLOC_CAP_DMA)` 直接失败；16384 字节能拿到。
   **音频缓冲必须分块，一块一两万字节**，不能一次分配整段。MP3 播放同理。

3. **别指望用软件"修"喇叭的频响。** 提高音量、加大数字增益、换采样率都试过，
   对"放不出来的频段"无效——那是物理限制。真要重做，得换一个**低中频成分更足**
   的素材（比如真实相机快门那种带机身共振的"咔哒"），或者换喇叭。

4. **诊断手段留下两个现成的**：`Settings → Test Speaker`（验证整条音频通路），
   以及 `tools/check_shutter_sound.py`（把固件里的 PCM 导出来在电脑上听）。
   以后"没声音"先跑这两个，能立刻分清是通路问题还是素材问题。
