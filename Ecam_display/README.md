# Ecam Status Display

> E_cam 项目上位机 —— API 用量反推 + 电脑硬件状态监控面板

一个单文件、零配置的桌面小工具（Python + Tkinter）。左边盯 API 余额和 Tokens 消耗，右边盯 CPU / 内存 / 显卡 / 网速，还能把整份状态通过串口实时推给 ESP32 副屏。

核心思路：**大多数 API 平台只告诉你"余额剩多少"，但你想知道"烧了多少 Tokens"。** 本项目靠两条恒等式 + 一个单价锚点，把余额变化实时翻译成 Tokens 消耗量。

## 功能特性

| 模块 | 说明 |
|---|---|
| **API 用量反推** | 由余额变化实时反推 Tokens 消耗，支持单价锁定 / 随动两种模式 |
| **全局联动计算** | 充值、单价、Tokens、已消费、余额 五项任意一项改动，其余项瞬间自动重算 |
| **多平台兼容** | 不绑定厂商，依次探测 OpenAI 兼容的常见计费端点；内置硅基流动 / DeepSeek / 通义 / 智谱 / 火山 / Kimi 预设 |
| **硬件监控** | CPU 占用、内存、NVIDIA 显卡占用率、网络上下行速度 |
| **串口推送** | 每秒一帧 JSON 推给 ESP32，副屏可直接显示 |
| **安全存储** | API Key 存入 Windows 凭据管理器（DPAPI 加密），不落盘明文 |
| **自动刷新** | 后台 10 秒轮询余额，可随时关闭；关闭后线程彻底挂起，0 CPU / 0 网络占用 |

## 快速开始

### 环境要求

- Windows（串口推送与凭据管理器依赖 Windows；纯 API 面板部分跨平台可用）
- Python 3.8+
- 可选：NVIDIA 显卡 + 最新驱动（用于 GPU 监控）

### 安装依赖

```bash
pip install requests psutil pyserial pynvml keyring
```

| 包 | 用途 | 缺失后果 |
|---|---|---|
| `psutil` | CPU / 内存 / 网络采集 | **必需**，缺失直接退出 |
| `pyserial` | 串口推送 | **必需**，缺失直接退出 |
| `keyring` | API Key 加密存储 | 可选，缺失时退回 json 内 Base64（不安全） |
| `pynvml` | NVIDIA 显卡读取 | 可选，缺失时回退 `nvidia-smi`；再失败则 GPU 显示 `N/A` |

### 运行源码

```bash
python Ecam_Status_Display.py
```

### 打包为 EXE

直接右键 **以管理员身份运行** `build.bat`，完成后 exe 位于 `dist\`。

脚本会自动安装依赖 → 清理旧构建 → 注入隐藏模块（`keyring.backends.Windows`、`pynvml`、`psutil`、`serial`）→ 打包。

> ⚠️ 打包后配置写在 **exe 所在目录**（而非 PyInstaller 的临时解包目录），所以 exe 换个位置，配置是要跟着搬的。

## 使用方法

### 1. 配置 API

界面顶部两栏：

- **接口地址**：下拉选预设，或手填任意 OpenAI 兼容地址
- **API Key**：粘贴密钥，输入框显示为圆点

程序**关闭时**会把 Key 写入系统凭据管理器，下次启动自动填回，无需重输。

### 2. 采集余额

- **自动刷新**（勾选框）：每 10 秒拉一次余额。取消勾选后后台线程彻底休眠。
- **立即刷新**：强制拉取最新余额，并**强制触发本地重算**——改完充值或单价后点它最省事。

### 3. 追踪 Tokens 消耗

这是本工具的核心流程，四步：

```
① 填入「充值金额」        例如 60
② 等余额拉回来            例如 55
③ 程序自动算出已消费      60 − 55 = 5 元
④ 点「锁定单价」钉住锚点   此后 Tokens 随余额实时反推
```

第 ④ 步是关键：**不锁定的话，单价会随数据变化漂移；锁定后单价成为固定锚点，Tokens 才会随每次余额刷新而跳动。**

> 单价从哪来？可以手填（问平台客服或查价目表），也可以先让程序按当前数据反推出来，再一键锁定。

### 4. 全局联动

五个输入框任意一个改动后，**点击界面空白处、切换到别的输入框、或点「立即刷新」**，都会瞬间触发重算。不需要等网络请求。

### 5. 串口推送

1. 下拉选择串口（自动枚举，显示为 `COMx - 描述`）
2. 点 **开始传递数据** → 建立 115200 连接，每秒推送一帧 JSON
3. 再点一次（此时按钮变红显示 **停止传递数据**）即断开

## 核心算法

### 两条恒等式

整个程序只建立在两条关系上，任何时候都成立：

```
已消费 C = 充值 R − 余额 B          …… ① 余额守恒
已消费 C = Tokens T × 单价 P ÷ 10⁶  …… ② 计费换算
```

其中 **单价 P 的单位是「元 / 百万 Tokens」**（代码内部统一换算成 `P/1e6` 元/Token）。

五个变量中，只要已知任意三个，剩下两个就能解出来。程序做的事就是：**判断哪几个是可信锚点，把其余的推出来。**

### 锚点优先级

程序给每个字段维护一个来源标记 `field_mode`：

| 标记 | 含义 | 是否可信锚点 |
|---|---|---|
| `api` | 接口返回的 | ✅ 是 |
| `manual` | 用户手填的 | ✅ 是 |
| `calc` | 程序算出来的 | ❌ 否，可被覆盖 |

**可信锚点永远不会被计算结果覆盖**，这保证了你手填的数据不会被程序悄悄改掉。

### 模式 A：单价锁定

**触发条件**：单价来源是 `manual` 且 `P > 0`（即点过「锁定单价」）。

以 **充值 R、余额 B、单价 P** 为锚：

```
C = R − B
T = C × 10⁶ ÷ P
```

关键行为：**Tokens 会被强制降级为派生量**——即使它原本来自接口或手填，也会被覆盖掉。

这看起来反直觉，但正是"实时性"的来源：单价钉死后，`T` 完全由 `C = R − B` 决定，所以**改充值或刷新余额，Tokens 立刻跟着跳**。如果不覆盖，你手填的旧 Tokens 会赖着不动。

余额缺失时反向补：`B = R − C`。

### 模式 B：单价随动

**触发条件**：单价未锁定。

此时以 **Tokens T、已消费 C、余额 B** 中已知的项为锚，先把单价反推出来：

```
P = C × 10⁶ ÷ T          （C 未知时用 R − B 代替）
```

拿到 P 之后，**最多迭代 4 轮**补齐未知项，每轮依次尝试：

```
T 已知 且 P > 0 且 C 未知  →  C = T × P ÷ 10⁶      ①
C 已知 且 P > 0 且 T 未知  →  T = C ÷ (P ÷ 10⁶)    ②
R 已知 且 C 已知 且 B 未知  →  B = R − C            ③
R 已知 且 B 已知 且 C 未知  →  C = R − B            ④
```

任意一轮没有任何字段变化就提前退出，所以实际通常 1~2 轮就收敛。算出的 P 会回填到单价框（标记为 `calc`，下次数据变化时允许重新反推）。

### 充值金额的自动推断

充值框留空时，若 **已消费和余额都已知**，程序自动推断：

```
R = C + B
```

所以哪怕忘了充了多少钱，只要知道花了多少、还剩多少，就能把 R 补回来。

### 完整流程图

```
                    ┌──────────────┐
                    │  API 拉取余额 │
                    └──────┬───────┘
                           │ B
                    ┌──────▼───────┐
                    │  单价已锁定？ │
                    └──┬────────┬──┘
                   是  │        │  否
              ┌────────▼──┐  ┌──▼─────────────┐
              │ 锚：R,B,P │  │ 锚：T/C/B 已知项 │
              │           │  │                │
              │ C = R − B │  │ P = C×10⁶ ÷ T  │
              │ T = C×10⁶ │  │      ↓         │
              │     ÷ P   │  │ 迭代 4 轮补齐   │
              └─────┬─────┘  └────────┬───────┘
                    │                 │
                    └────────┬────────┘
                             ▼
                   ┌───────────────────┐
                   │ 界面联动刷新       │
                   │ (可信锚点不被覆盖) │
                   └───────────────────┘
```

### 一个具体例子

```
充值 R = 60 元
单价 P = 0.07 元/百万 Tokens
```

| 时刻 | 余额 B | 已消费 C = 60 − B | Tokens T = C×10⁶ ÷ 0.07 |
|---|---|---|---|
| 刚充值 | 60.00 | 0.00 | 0 |
| 跑了一会 | 59.65 | 0.35 | 5,000,000 |
| 又跑一会 | 59.30 | 0.70 | 10,000,000 |

单价锁定后，**每次余额刷新都会立刻换算成 Tokens 跳数**，无需任何手动干预。

## 串口协议

波特率 **115200**，每秒发送一行 UTF-8 JSON（`\n` 结尾）：

```json
{
  "type": "status",
  "host": "DESKTOP-XXXX",
  "cpu": 23.5,
  "ram": 61.2,
  "gpu": 45,
  "net_up": 12.3,
  "net_down": 456.7,
  "battery": 100,
  "api": {
    "base_url": "https://api.deepseek.com",
    "key_set": true,
    "tokens": 10000000,
    "cost": 0.7,
    "balance": 59.3
  },
  "ts": 1727174400
}
```

| 字段 | 类型 / 单位 | 说明 |
|---|---|---|
| `type` | string | 固定为 `"status"`，便于副屏分流其他消息 |
| `host` | string | 主机名（`platform.node()`） |
| `cpu` / `ram` | float / % | CPU 占用率 / 内存占用率，保留 1 位小数 |
| `gpu` | int / % | NVIDIA 显卡占用率；**无 N 卡或读取失败时为 `-1`** |
| `net_up` / `net_down` | float / KB/s | 实时速度（由累计字节数差分算出），保留 1 位小数 |
| `battery` | int / % | 电量百分比；**无电池或读取失败时为 `-1`** |
| `api.tokens` | int | 反推的 Tokens 消耗量，取不到为 `null` |
| `api.cost` / `api.balance` | float / 元 | 保留 4 位小数，取不到为 `null` |
| `api.key_set` | bool | **只报"有没有配 Key"，不含 Key 本身** |
| `ts` | int / 秒 | Unix 时间戳 |

> 副屏解析提示：`gpu` 和 `battery` 用 `-1` 表示不可用（而非 `null`），判断时注意区分 `-1` 和真实值 `0`。

> 🔒 协议里**永远不包含 API Key 内容**，只用一个 `key_set` 布尔值表示是否已配置。

## 配置文件

`ecam_config.json` 与程序同目录：

```json
{
  "base_url": "https://api.deepseek.com",
  "recharge": "60",
  "price": "0.07",
  "api_key_b64": ""
}
```

只保存**非敏感**数据（接口地址、充值金额、单价）。API Key 走系统凭据管理器，此文件中的 `api_key_b64` 正常情况下为空字符串。

> ⚠️ 仅在**未安装 keyring** 时，Key 才会以 Base64 写进 `api_key_b64`（Base64 只是编码不是加密，等同于明文）。**该文件已加入 `.gitignore`，请勿提交。**

## 常见问题

| 现象 | 原因 | 解决 |
|---|---|---|
| GPU 显示 `N/A` | 非 N 卡 / 没装驱动 / 权限不足 | 确认是 N 卡；更新驱动并 `pip install pynvml`；尝试管理员运行 |
| API Key 没记住 | 打包时漏了隐藏模块 | 确认 `build.bat` 含 `--hidden-import=keyring.backends.Windows` |
| 点刷新没反应 | 网络延迟或接口限流 | 看底部日志栏；提示限流就等几秒再试 |
| 改充值金额 Tokens 不变 | 未触发本地重算 | 点界面空白处，或点「立即刷新」强制联动 |
| 点「停止传递数据」报串口被占用 | v3.9 以前的状态标志缺失 bug | 已修复，请使用当前版本 |
| Tokens 一直显示 `--` | 单价未锁定 / 锚点不足 | 至少填满五项中的三项，或点「锁定单价」 |
| 余额能拉到但 Tokens 拉不到 | 该平台接口不提供用量字段 | 正常现象——余额够用，Tokens 靠本工具反推 |

## 安全性说明

- API Key 存储在 **Windows 凭据管理器**（DPAPI），加密且绑定当前用户账户，换台电脑解不开
- 因此**整个文件夹打包发给别人也不会泄露 Key**
- 串口协议只传 `key_set` 布尔值，不传 Key 内容
- `ecam_config.json` 已加入 `.gitignore`，防止 Base64 兜底数据误提交
- 若确实未安装 `keyring`，程序会在界面上提示"Key 将退回 Base64 存储"
